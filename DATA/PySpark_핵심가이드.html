PySpark 핵심 가이드

분산 DataFrame의 실행 모델부터 성능 튜닝, 메서드 치트 시트까지

Spark 4.x 기준 · 모든 예제 PySpark 4.2.0에서 실행 검증 · 2026-09

들어가며

이 책은 pandas에 익숙한 Python 개발자가 PySpark를 빠르게, 그러나 제대로 익히도록 쓰였습니다. Python 문법이나 DataFrame이라는 개념 자체는 설명하지 않습니다. 대신 “pandas처럼 생겼는데 왜 다르게 동작하는가”에 지면을 씁니다.

대상 버전. Spark 4.x(예제는 4.2.0에서 실제로 실행해 출력을 붙였습니다). 3.5에서도 대부분 동작하며, 4.0에서 바뀐 부분은 따로 표시합니다.

읽는 순서.

  • 1–2장: 아키텍처와 실행 모델. 가장 중요합니다. 여기를 건너뛰면 나머지가 전부 “마법”으로 보입니다.
  • 3–8장: DataFrame API와 SQL. 매일 쓰는 도구입니다.
  • 9–10장: pandas 연동과 성능. 실무에서 차이가 나는 곳입니다.
  • 11–13장: RDD, 스트리밍, 배포·운영.
  • 부록: pandas→PySpark 번역표, 메서드 치트 시트.

표기. 모든 예제는 다음 import를 전제합니다.

from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql import types as T
from pyspark.sql.window import Window

F, T 별칭은 PySpark 커뮤니티의 사실상 표준입니다. from pyspark.sql.functions import *는 sum, max, round 같은 Python 내장 함수를 덮어쓰므로 쓰지 마십시오.

로컬 환경 준비. Java 17 또는 21이 필요합니다. pip install "pyspark[sql]" 한 줄이면 클러스터 없이 노트북에서 모든 예제를 돌릴 수 있습니다. [sql]은 pandas·pyarrow를 함께 설치합니다. PySpark 4.2는 아직 pandas 3.x를 완전히 지원하지 않아 경고를 띄우므로, pandas는 2.x 버전을 권합니다.

1 Spark는 무엇이고 어떻게 생겼나

1.1 pandas와 결정적으로 다른 세 가지

pandas DataFrame은 한 프로세스의 메모리에 있는 실제 데이터입니다. df["a"] + 1을 쓰는 순간 계산이 끝나고 결과가 메모리에 생깁니다.

Spark DataFrame은 셋 다 다릅니다.

  1. 분산되어 있습니다. 데이터는 여러 머신의 여러 프로세스에 파티션 단위로 쪼개져 있습니다. 한 곳에 모이는 일은 원칙적으로 없습니다.
  2. 게으릅니다(lazy). df.filter(...)는 아무것도 계산하지 않고 “이렇게 계산하겠다”는 계획만 반환합니다. 실제 계산은 count(), show(), write 같은 액션을 부를 때 일어납니다.
  3. 불변입니다. 모든 변환은 새 DataFrame(=새 계획)을 반환합니다. inplace=True 같은 것은 없습니다.

한마디로, Spark DataFrame은 데이터가 아니라 쿼리입니다. SQL의 VIEW에 더 가깝습니다. 이 관점만 잡으면 이 책의 절반은 이해한 셈입니다.

1.2 구성 요소

Driver. 여러분의 Python 스크립트가 실행되는 프로세스입니다. SparkSession을 갖고 있으며, DataFrame 연산을 받아 논리 계획 → 최적화 → 물리 계획으로 바꾸고, 이를 작은 작업(Task)으로 쪼개 Executor에 나눠 줍니다. Driver는 데이터를 거의 만지지 않습니다. 단, collect()·toPandas()를 부르면 결과 전체가 Driver 메모리로 옵니다. Driver OOM의 대부분이 여기서 납니다.

Executor. 워커 노드에서 도는 JVM 프로세스입니다. 파티션 하나를 처리하는 단위가 Task이고, Executor는 코어 수만큼 Task를 동시에 돌립니다. 캐시된 데이터와 셔플 중간 파일도 Executor가 들고 있습니다.

Cluster Manager. Executor를 띄울 자원(CPU·메모리)을 빌려주는 쪽입니다. YARN, Kubernetes, Spark Standalone이 있고, 학습용 local[*] 모드는 Driver 프로세스 안의 스레드를 Executor처럼 씁니다.

분산 DB 경험과의 대응. Driver는 쿼리 코디네이터, Executor는 데이터 노드의 쿼리 워커와 비슷합니다. 다른 점은, Spark는 저장소를 소유하지 않는다는 것입니다. 데이터는 S3·HDFS·DB 등 바깥에 있고, Spark는 매 작업마다 읽어 와서 계산만 합니다. “스토리지와 컴퓨트의 분리”가 기본값입니다.

1.3 Python은 어디서 도는가

Spark 엔진은 JVM(Scala)으로 짜여 있습니다. PySpark의 DataFrame API는 JVM 객체를 조종하는 얇은 리모컨입니다. df.filter(F.col("x") > 1)은 Python에서 식을 만들 뿐이고, 실제 필터링은 JVM의 최적화된 코드가 수행합니다. 그래서 DataFrame API만 쓰면 PySpark도 Scala만큼 빠릅니다.

예외가 Python UDF입니다. 사용자 정의 Python 함수는 JVM이 실행할 수 없으므로, Executor 옆에 Python 워커 프로세스를 띄워 행을 직렬화해 보내고, 결과를 다시 받아옵니다. 이 왕복이 비쌉니다. 9장에서 다룹니다.

1.4 SparkSession: 모든 것의 입구

from pyspark.sql import SparkSession

spark = (
    SparkSession.builder
    .appName("my-app")
    .master("local[4]")   # 로컬 스레드 4개
    .config("spark.sql.shuffle.partitions", "8")
    .getOrCreate()
)
print(spark.version)
4.2.0
  • getOrCreate()는 이미 세션이 있으면 그것을 돌려줍니다. 노트북에서 설정을 바꿔 다시 실행해도 기존 세션이 재사용되어 설정이 안 먹는 흔한 함정이 여기서 생깁니다. 이미 떠 있는 세션의 정적 설정을 바꾸려면 spark.stop() 후 다시 만드십시오.
  • .master(...)는 로컬 학습 때만 씁니다. 운영에서는 spark-submit이나 플랫폼(Databricks, EMR 등)이 정해 주므로 코드에 박지 않습니다.
  • spark.sparkContext는 RDD 시절의 저수준 진입점입니다. 요즘은 로그 레벨 설정 정도에만 씁니다.

1.5 Spark Connect

Spark 3.4부터 도입되고 4.x에서 본격화된 클라이언트–서버 모드입니다. Driver가 원격 서버에 있고, 내 Python 프로세스는 gRPC로 미해결 논리 계획(unresolved plan) 만 보냅니다.

spark = (SparkSession.builder
         .remote("sc://spark-host:15002")
         .getOrCreate())
  • 클라이언트가 가볍습니다(pip install pyspark-client, JVM 불필요).
  • 클라이언트가 죽어도 서버는 멀쩡합니다. 여러 사용자가 한 서버를 공유하기 좋습니다.
  • 제약: sparkContext와 RDD API를 쓸 수 없습니다. DataFrame/SQL 중심으로 코드를 쓰는 습관이 곧 이식성입니다.

Databricks의 서버리스·공유 클러스터도 내부적으로 이 모드입니다. 이 책의 예제는 11장(RDD)을 빼면 Connect에서도 그대로 돌아갑니다.

1.6 핵심 정리

  • Spark DataFrame은 분산·게으름·불변. 데이터가 아니라 쿼리입니다.
  • Driver가 계획하고 Executor가 실행합니다. collect()는 Driver로 데이터를 끌고 옵니다.
  • DataFrame API는 JVM에서 실행되어 빠르고, Python UDF만 예외적으로 느립니다.

2 실행 모델: 게으름, 계획, 셔플

이 장은 이론처럼 보이지만 성능 문제의 90%가 여기서 설명됩니다. 천천히 읽으십시오.

2.1 변환(Transformation)과 액션(Action)

DataFrame 메서드는 두 부류입니다.

구분 반환 예 실행
변환 새 DataFrame select, filter, withColumn, join, groupBy().agg(), orderBy 안 함 (계획만)
액션 값·부수효과 count, show, collect, take, first, toPandas, write...save() 즉시 실행 
from pyspark.sql import functions as F

df = spark.range(0, 10_000_000)        # 0..9,999,999
big = df.withColumn("sq", F.col("id") * F.col("id"))
evens = big.filter(F.col("id") % 2 == 0)
# 여기까지 실행된 계산: 없음
print(evens.count())         # 이 순간 전부 실행
5000000

evens를 만드는 데는 몇 밀리초도 걸리지 않습니다. 천만 행을 제곱하고 거르는 일은 count()를 부를 때 한꺼번에 일어납니다.

2.1.1 왜 게으른가

게으름은 최적화 기회입니다. 액션 시점에는 Spark가 전체 파이프라인을 한눈에 볼 수 있으므로,

  • 필터를 가능한 한 앞으로 당기고(predicate pushdown), 파일 읽을 때부터 걸러냅니다.
  • 쓰지 않는 컬럼은 아예 읽지 않습니다(column pruning).
  • 연속된 withColumn·filter를 하나의 루프로 합칩니다(whole-stage codegen).

pandas에서는 한 줄 한 줄이 중간 결과를 메모리에 만들지만, Spark에서는 중간 결과가 없습니다.

2.1.2 반복 액션의 함정

반대로 말하면, 액션을 부를 때마다 계획 전체가 처음부터 다시 실행됩니다.

cleaned = raw.filter(...).join(...).groupBy(...).agg(...)
cleaned.count()          # 전체 실행 1회
cleaned.show()           # 전체 실행 2회 (처음부터!)
cleaned.write.parquet()  # 전체 실행 3회

같은 결과를 여러 번 쓸 거라면 cache()로 한 번 계산한 결과를 붙잡아 두어야 합니다(10장). 디버깅한다고 중간중간 count()를 넣는 습관이 파이프라인을 몇 배 느리게 만드는 주범입니다.

2.2 계획 들여다보기: explain()

df1 = spark.range(100).withColumn("g", F.col("id") % 3)
q = (df1.filter(F.col("id") > 10)
        .groupBy("g").agg(F.sum("id").alias("s")))
q.explain()
== Physical Plan ==
AdaptiveSparkPlan isFinalPlan=false
+- HashAggregate(keys=[g#9L], functions=[sum(id#8L)])
   +- Exchange hashpartitioning(g#9L, 8), ENSURE_REQUIREMENTS, [plan_id=58]
      +- HashAggregate(keys=[g#9L], functions=[partial_sum(id#8L)])
         +- Project [id#8L, (id#8L % 3) AS g#9L]
            +- Filter (id#8L > 10)
               +- Range (0, 100, step=1, splits=4)

아래에서 위로 읽습니다. Range → Filter → Project → HashAggregate(partial) → Exchange → HashAggregate(final).

AdaptiveSparkPlan isFinalPlan=false는 실행 중에 계획이 바뀔 수 있다는 뜻입니다(AQE, 10장). 옵티마이저의 각 단계를 모두 보려면 q.explain(mode="extended"), 읽기 좋은 형태는 mode="formatted"입니다.

2.2.1 Catalyst 옵티마이저

여러분이 쓴 DataFrame 코드는 다음 단계를 거칩니다.

  1. 미해결 논리 계획: 컬럼 이름이 실제 있는지 아직 모름.
  2. 분석된 논리 계획: 카탈로그/스키마와 대조해 이름·타입 확정. 오타가 있으면 여기서 AnalysisException.
  3. 최적화된 논리 계획: 규칙 기반 최적화(필터 푸시다운, 상수 접기, 불필요한 프로젝션 제거 등).
  4. 물리 계획: 조인 알고리즘 선택 등. 통계를 참고합니다(CBO).
  5. 코드 생성: JVM 바이트코드.

SQL로 쓰든 DataFrame API로 쓰든 2단계부터 똑같습니다. SQL과 DataFrame API 사이에 성능 차이는 없습니다. 편한 쪽을 쓰면 됩니다.

분석(2단계)은 변환을 만드는 시점에 즉시 일어납니다. 그래서 없는 컬럼을 참조하면 액션 전에도 바로 에러가 납니다. “게으르다”는 것은 데이터 처리가 게으르다는 뜻입니다.

2.3 파티션: 병렬성의 단위

DataFrame은 파티션들의 모음입니다. 파티션 하나 = Task 하나 = 코어 하나가 처리하는 덩어리.

df2 = spark.range(0, 1000, numPartitions=6)
print(df2.rdd.getNumPartitions())
6
  • 파일을 읽으면 대략 128MB(spark.sql.files.maxPartitionBytes)당 파티션 하나가 생깁니다.
  • 파티션이 너무 적으면 코어가 놀고, 한 Task가 메모리를 넘칩니다.
  • 너무 많으면 Task 스케줄링 오버헤드와 작은 파일 문제가 생깁니다.
  • 경험칙: 파티션당 100–200MB, 파티션 수는 총 코어 수의 2–4배.

2.4 좁은 변환과 넓은 변환

좁은 변환은 입력 파티션 하나가 출력 파티션 하나만 만듭니다. 각 Executor가 자기 데이터만 보고 끝냅니다. 여러 개가 이어져도 한 번에 파이프라이닝됩니다.

넓은 변환은 같은 키를 가진 행을 한곳에 모아야 합니다. groupBy("user")라면 모든 파티션에 흩어진 user=42의 행이 한 파티션으로 가야 하지요. 이 재배치가 셔플(shuffle) 이고, explain()의 Exchange가 바로 셔플입니다.

셔플은 Spark에서 가장 비싼 연산입니다.

  1. 각 Executor가 행을 키 해시로 나눠 로컬 디스크에 씁니다(shuffle write).
  2. 다음 단계의 Task들이 네트워크로 모든 Executor에서 자기 몫을 가져옵니다(shuffle read).
  3. 직렬화·압축·정렬 비용이 따릅니다.

셔플 후 파티션 수는 spark.sql.shuffle.partitions(기본 200)가 정합니다. 요즘은 AQE가 실행 중에 작은 파티션을 합쳐 주므로 이 값에 덜 민감합니다.

2.5 Job, Stage, Task

액션 하나가 Job 하나를 만듭니다(가끔 여러 개). Job은 셔플 경계에서 Stage로 나뉩니다. Stage 안은 좁은 변환만 있으니 파이프라이닝되고, Stage는 파티션 수만큼의 Task로 실행됩니다.

q.collect()                      ← Job 1개
 ├─ Stage 0: Range → Filter → partial agg
 │   · Task 수 = 입력 파티션 수
 │   · 끝에서 shuffle write
 └─ Stage 1: shuffle read → final agg
     · Task 수 = 셔플 파티션 수

Spark UI(로컬은 http://localhost:4040)의 Jobs/Stages 탭이 정확히 이 구조를 보여 줍니다. 느린 작업을 조사할 때는 13장의 요령대로 가장 오래 걸린 Stage → 그 안에서 가장 오래 걸린 Task를 찾아 내려가십시오.

2.6 핵심 정리

  • 변환은 계획, 액션은 실행. 액션마다 처음부터 다시 계산합니다.
  • explain()으로 계획을 읽는 습관을 들이십시오. Exchange = 셔플.
  • 파티션 = 병렬성 단위. 셔플은 Stage를 가르는 비싼 경계입니다.
  • 성능 튜닝은 대부분 셔플을 줄이거나, 셔플을 고르게 만드는 일입니다.

3.4 Column 표현식

Spark 연산의 기본 단위는 값이 아니라 Column 표현식입니다. 컬럼을 가리키는 방법은 넷입니다.

people.select("age")            # 문자열
people.select(people.age)       # 속성
people.select(people["age"])    # 인덱싱
people.select(F.col("age"))     # 함수 (가장 권장)

F.col("age")는 특정 DataFrame에 묶이지 않은 표현식이라 재사용과 체이닝에 유리합니다. people.age는 조인 후 이름이 겹칠 때 어느 쪽 컬럼인지 지정하는 용도로 씁니다. 속성 방식은 count, name 같은 DataFrame 메서드 이름과 충돌하므로 피하십시오.

표현식은 연산자로 조립합니다.

people.select(
    "name",
    F.round(F.col("salary") * 1.1, 1).alias("raised"),
    (F.col("age") >= 30).alias("senior"),
    F.lit("KR").alias("country"),
    F.concat_ws("-", "city", "name").alias("key"),
).show()

논리 연산자는 &, |, ~이고 괄호가 필수입니다. Python의 and/or/not은 Column에 쓸 수 없습니다(에러). 또 &가 >=보다 우선순위가 높기 때문에 F.col("a") > 1 & F.col("b") < 2는 엉뚱하게 해석됩니다. 조건 하나하나를 반드시 괄호로 감싸십시오. pandas의 불리언 인덱싱과 같은 규칙입니다.

4.5 Parquet: 기본값으로 삼을 포맷

Parquet는 컬럼 지향 바이너리 포맷입니다. Spark 생태계의 사실상 표준이고, 특별한 이유가 없으면 중간·최종 결과를 모두 Parquet(또는 이를 기반으로 한 Delta/Iceberg)로 저장하십시오.

  • 스키마 내장: 타입 추론이 필요 없습니다.
  • 컬럼 프루닝: 필요한 컬럼만 디스크에서 읽습니다.
  • 프레디킷 푸시다운: 파일·row group마다 min/max 통계가 있어, WHERE amount > 10000에 해당하지 않는 블록은 건너뜁니다.
  • 압축: 기본 snappy. CSV보다 보통 수 배 작습니다.

          .drop("_corrupt_record") \

      .partitionBy("dt")
      .parquet(f"{base}/orders_pq"))

4.8 테이블 포맷: Delta Lake, Iceberg

Parquet 디렉터리는 편하지만 트랜잭션이 없습니다. 쓰기 도중 실패하면 반쯤 쓴 파일이 남고, 동시에 읽는 쪽은 깨진 상태를 봅니다. UPDATE·MERGE도 없습니다.

Delta Lake와 Apache Iceberg는 Parquet 파일 위에 트랜잭션 로그를 얹어 이 문제를 풉니다.

  • ACID 쓰기, 스냅숏 격리
  • MERGE INTO(upsert), UPDATE, DELETE
  • 타임 트래블(VERSION AS OF)
  • 스키마 진화, 파일 컴팩션
df.write.format("delta").mode("append").save(path)
spark.read.format("iceberg").load("catalog.db.tbl")

별도 패키지 설정이 필요하므로 이 책에서는 개념만 소개합니다. 새로 데이터 레이크를 설계한다면 둘 중 하나를 기본으로 삼으십시오.

4.9 JDBC: 데이터베이스 읽기

orders = (spark.read.format("jdbc")
    .option("url", "jdbc:postgresql://db:5432/shop")
    .option("dbtable", "public.orders")
    .option("user", user).option("password", pw)
    .option("partitionColumn", "order_id")
    .option("lowerBound", 1)
    .option("upperBound", 10_000_000)
    .option("numPartitions", 16)
    .option("fetchsize", 10_000)
    .load())

partitionColumn·경계·numPartitions를 주지 않으면 단일 커넥션, 단일 Task로 전체 테이블을 읽습니다. 분산 처리의 의미가 없어지지요. 위 설정은 order_id 범위를 16등분해 16개 쿼리를 병렬로 날립니다. 경계값은 필터가 아니라 분할 기준일 뿐이라 범위 밖 행도 첫/마지막 파티션에 포함됩니다. 원본 DB가 감당할 수 있는 동시 커넥션 수를 넘기지 않도록 numPartitions를 정하십시오.

dbtable 대신 query 옵션으로 서브쿼리를 줄 수도 있고, 이때 필터는 DB 쪽에서 실행됩니다.

4.10 핵심 정리

  • CSV/JSON은 스키마를 명시하고, mode로 불량 행 정책을 정하십시오.
  • 저장은 Parquet(가능하면 Delta/Iceberg). 컬럼·파티션 프루닝의 혜택을 받습니다.
  • 출력은 디렉터리입니다. partitionBy는 저카디널리티 필터 컬럼으로.
  • JDBC는 partitionColumn을 주지 않으면 병렬이 아닙니다.

6.2.1 부분 집계: groupBy가 생각보다 싼 이유

2장의 explain()에서 HashAggregate가 셔플 전후로 두 번 나온 것을 기억하십니까? Spark는 셔플 전에 각 파티션에서 부분합(partial)을 먼저 계산하고, 셔플로는 그 부분합만 보냅니다. MapReduce의 combiner와 같은 아이디어입니다. 그래서 sum·count·max는 원본 행 수와 무관하게 셔플량이 그룹 수 × 파티션 수 정도로 작습니다.

반면 collect_list와 정확한 countDistinct는 값 자체를 셔플해야 해서 비쌉니다. 그룹 하나가 거대하면 한 Task의 메모리를 넘칠 수도 있습니다.

6.4 조인 전략: Spark는 어떻게 조인하는가

분산 환경에서 조인은 같은 키의 행을 같은 곳에 모으는 문제입니다. Spark의 선택지는 크게 둘입니다.

Broadcast Hash Join (BHJ). 한쪽이 작으면 그 테이블 전체를 모든 Executor에 복사합니다. 큰 쪽은 움직이지 않고 제자리에서 해시 조회만 하면 됩니다. 셔플이 없으므로 가장 빠릅니다. 기본적으로 한쪽 추정 크기가 spark.sql.autoBroadcastJoinThreshold(기본 10MB) 이하면 자동 선택됩니다.

Sort Merge Join (SMJ). 둘 다 크면 양쪽을 키로 셔플하고, 파티션 안에서 정렬해 병합합니다. 셔플 두 번 + 정렬이라 비싸지만 메모리 걱정 없이 어떤 크기든 처리합니다. 큰 테이블끼리의 기본 전략입니다.

(키 쪽 파티션이 메모리에 들어갈 만하면 정렬 없이 해시 테이블을 만드는 Shuffle Hash Join도 있습니다.)

names = F.array(*[F.lit(u) for u in

big = spark.range(1_000_000).withColumn(

브로드캐스트되는 쪽은 Driver를 거쳐 모든 Executor에 보내집니다. 수백 MB를 넘기면 Driver OOM이나 브로드캐스트 타임아웃이 납니다. “작은 쪽”의 기준은 대략 수십 MB, 크게 잡아도 수백 MB까지입니다. 또 left 조인에서는 오른쪽만 브로드캐스트할 수 있습니다(왼쪽을 복사하면 매칭 안 된 행이 중복 출력되므로).

6.6 핵심 정리

  • 집계 결과 컬럼은 alias로 이름 붙이기. sum/count는 부분 집계로 쌉니다.
  • left_semi/left_anti는 존재 여부 필터의 정석입니다.
  • 작은 쪽은 브로드캐스트(셔플 없음), 큰 쪽끼리는 Sort Merge(셔플 2회).

  • union 대신 unionByName.

7.4 누적과 이동 집계: 프레임

집계 함수에 .over(w)를 붙이면 윈도 집계가 됩니다. 이때 프레임이 중요합니다.

running = w.rowsBetween(Window.unboundedPreceding,
                        Window.currentRow)
moving2 = w.rowsBetween(-1, Window.currentRow)
whole = Window.partitionBy("user")

    "user", "amount",
    F.sum("amount").over(running).alias("cum"),
    F.avg("amount").over(moving2).alias("mv2"),
    F.sum("amount").over(whole).alias("user_total"),
    (F.col("amount") / F.sum("amount").over(whole))
      .alias("share"),
).show()

|user|amount| cum|  mv2|user_total|              share|

| kim|   100| 100|100.0|       600|0.16666666666666666|
| kim|   300| 400|200.0|       600|                0.5|
| kim|   200| 600|250.0|       600| 0.3333333333333333|
| lee|   500| 500|500.0|      1100|0.45454545454545453|
| lee|   500|1000|500.0|      1100|0.45454545454545453|
| lee|   100|1100|300.0|      1100|0.09090909090909091|
+----+------+----+-----+----------+-------------------+
  • rowsBetween(a, b): 행 개수 기준. -1은 한 행 앞.
  • rangeBetween(a, b): orderBy 값 기준. “현재 시각부터 1시간 전까지”처럼 값의 범위로 자를 때. orderBy 컬럼이 하나이고 숫자여야 하므로 타임스탬프는 cast("long")(초)로 바꿔 씁니다.
  • orderBy가 없는 윈도(whole)는 파티션 전체가 프레임입니다. pandas의 groupby().transform("sum")과 같습니다.
hour = (Window.partitionBy("user")
        .orderBy(F.col("ts").cast("long"))
        .rangeBetween(-3600, 0))

          F.sum("amount").over(hour).alias("last_1h")) \
  .show()

| kim|2026-09-01 12:00:00|   200|    200|
| lee|2026-09-01 09:00:00|   500|    500|
| lee|2026-09-01 09:05:00|   500|   1000|
| lee|2026-09-02 18:00:00|   100|    100|
+----+-------------------+------+-------+

기본 프레임의 함정. orderBy가 있는 윈도에 프레임을 지정하지 않으면 기본값은 rangeBetween(unboundedPreceding, currentRow)입니다. 그래서 F.last("x").over(w)는 “파티션의 마지막 값”이 아니라 “현재 행까지의 마지막 값”, 즉 자기 자신을 돌려줍니다. 또 range 프레임이라 orderBy 값이 같은 행들(동점)은 한꺼번에 포함되어, 누적합이 계단처럼 뛸 수 있습니다. 누적합에는 rowsBetween을 명시하는 습관을 들이십시오.

7.5 윈도와 성능

윈도 함수는 partitionBy 키로 셔플한 뒤 파티션 안에서 정렬합니다. 비용 면에서 groupBy보다 무겁습니다.

  • partitionBy 없이 Window.orderBy(...)만 쓰면 모든 데이터가 한 파티션으로 모입니다. Spark가 경고(No Partition Defined for Window operation!)를 띄웁니다. 전역 순번이 꼭 필요하면 monotonically_increasing_id()(연속적이지 않은 고유 ID)로 대체할 수 있는지 먼저 검토하십시오.
  • 파티션 키 하나에 행이 몰리면(예: user = 'guest') 그 Task만 한없이 느려집니다. 10장의 데이터 스큐를 보십시오.
  • 같은 partitionBy/orderBy를 쓰는 윈도 함수 여러 개는 Spark가 한 번의 정렬로 묶어 처리합니다. 윈도 정의를 변수로 재사용하면 이 최적화를 받기 쉽습니다.

7.6 시간 버킷 집계: F.window

이름이 비슷하지만 다른 기능입니다. 타임스탬프를 고정 크기 구간으로 잘라 groupBy 키로 씁니다. 스트리밍(12장)에서 특히 많이 씁니다.

| kim|2026-09-01 10:00:00| 400|
| kim|2026-09-01 12:00:00| 200|
| lee|2026-09-01 09:00:00|1000|
| lee|2026-09-02 18:00:00| 100|

7.7 핵심 정리

  • 윈도 = partitionBy + orderBy + frame. 행 수가 유지됩니다.
  • 키별 최신 1건: row_number().over(...desc) → filter(rn == 1).
  • 누적은 rowsBetween을 명시. last의 기본 프레임 함정 주의.
  • partitionBy 없는 윈도는 단일 파티션으로 몰립니다.

9 UDF와 pandas 연동

9.1 Python UDF: 왜 느린가

내장 함수로 도저히 표현이 안 되는 로직은 Python 함수로 작성해 UDF(User Defined Function)로 등록할 수 있습니다.

from pyspark.sql import functions as F
from pyspark.sql import types as T

@F.udf(returnType=T.StringType())
def mask_email(s):
    if s is None:
        return None
    local, _, domain = s.partition("@")
    stars = "*" * (len(local) - 2)
    return local[:2] + stars + "@" + domain

df = spark.createDataFrame(
    [("kimminsu@a.com",), ("lee@b.com",), (None,)],
    "email STRING")
df.select(mask_email("email").alias("masked")).show()
+--------------+
|        masked|
+--------------+
|ki******@a.com|
|     le*@b.com|
|          NULL|
+--------------+

편리하지만 비용이 큽니다. 1장에서 본 것처럼 Python 함수는 JVM에서 실행할 수 없으므로,

  1. Executor(JVM)가 행을 직렬화해 옆의 Python 워커 프로세스로 보내고,
  2. Python이 한 행씩 함수를 호출하고,
  3. 결과를 다시 직렬화해 JVM으로 돌려보냅니다.

게다가 옵티마이저에게 UDF는 블랙박스입니다. 필터 푸시다운이나 상수 접기 같은 최적화가 UDF를 통과하지 못합니다.

UDF 작성 시 주의. ① None 입력을 반드시 처리하십시오. ② returnType과 실제 반환 타입이 다르면 에러 없이 null이 됩니다(예: IntegerType인데 float 반환). ③ 함수가 참조하는 전역 객체는 pickle되어 모든 Task로 전송됩니다. 큰 모델·사전을 클로저로 잡으면 매 Task마다 전송 비용이 듭니다.

9.2 pandas UDF: 벡터화된 UDF

pandas UDF는 행 단위 대신 Arrow 배치 단위로 데이터를 주고받고, 함수는 pd.Series를 받아 pd.Series를 돌려줍니다. 직렬화가 컬럼 기반이라 싸고, 함수 안에서 pandas/NumPy의 벡터 연산을 쓸 수 있어 Python 호출 횟수가 급감합니다.

import pandas as pd

@F.pandas_udf("string")
def mask_email_vec(s: pd.Series) -> pd.Series:
    m = s.str.extract(r"^(.{0,2})(.*)@(.*)$")
    stars = m[1].str.replace(r".", "*", regex=True)
    return m[0] + stars + "@" + m[2]

df.select(mask_email_vec("email").alias("masked")).show()
+--------------+
|        masked|
+--------------+
|ki******@a.com|
|     le*@b.com|
|          NULL|
+--------------+

함수는 배치마다 호출됩니다. 배치에 null만 있거나 행이 0개일 수도 있으니, 컬럼 구조가 입력 내용에 따라 바뀌는 연산(str.partition 같은)은 피하고 벡터 연산으로 작성하십시오.

타입 힌트가 UDF의 종류를 결정합니다.

시그니처 종류 용도
Series -> Series 스칼라 행 단위 변환 (길이 동일)
Iterator[Series] -> Iterator[Series] 스칼라(반복자) 배치마다 무거운 초기화(모델 로딩)를 한 번만
Series -> 스칼라 집계 groupBy().agg(), 윈도 안에서 사용 
@F.pandas_udf("double")
def trimmed_mean(v: pd.Series) -> float:
    q1, q9 = v.quantile(0.1), v.quantile(0.9)
    return float(v[(v >= q1) & (v <= q9)].mean())

nums = spark.range(1, 101).selectExpr(

9.3 얼마나 차이 나는가

같은 계산을 네 가지 방식으로 돌려 보겠습니다(로컬 4코어, 500만 행, 3회 중 최솟값). 첫 실행은 Python 워커 기동 비용이 섞이므로 반복 측정합니다.

import time

    (F.col("id") % 1000).cast("double").alias("x"))

    return x * 2.0 + 1.0

@F.udf("double", useArrow=True)
def plus_arrow(x):
    return x * 2.0 + 1.0

@F.pandas_udf("double")
def plus_pd(x: pd.Series) -> pd.Series:
    return x * 2.0 + 1.0

def bench(label, col, n=3):
    best = float("inf")
    for _ in range(n):
        t = time.perf_counter()
        big.select(F.sum(col)).collect()
        best = min(best, time.perf_counter() - t)
    print(f"{label:<12}{best:6.2f}s")

  1. 내장 함수(F.*, SQL 함수, 고차 함수)로 표현할 수 있으면 그것을 쓴다.
  2. 안 되면 pandas UDF (벡터화할 수 있는 로직).
  3. 행 단위 Python 로직이 꼭 필요하면 Python UDF. useArrow=True(3.5+)로 Arrow 직렬화를 켤 수 있습니다. 이 책의 실행 환경(4.2.0)에서는 spark.sql.execution.pythonUDF.arrow.enabled가 이미 기본 true라 일반 @F.udf도 Arrow로 직렬화되었고, 그래서 위 측정에서 두 UDF의 차이가 작습니다. 3.5 등 이전 버전은 기본값이 false이니 사용하는 버전에서 확인하십시오.

9.4 DataFrame 단위의 pandas 함수

9.4.1 applyInPandas: 그룹별 pandas 처리

groupBy(...).applyInPandas(func, schema)는 그룹 하나를 통째로 pd.DataFrame으로 넘깁니다. 그룹별 모델 학습, 그룹 내 보간, 복잡한 시계열 처리 등에 씁니다.

sales = spark.createDataFrame([
    ("A", 1, 10.0), ("A", 2, None), ("A", 3, 30.0),
    ("B", 1, 5.0),  ("B", 2, 7.0),  ("B", 3, None),
], "store STRING, day INT, amt DOUBLE")

def fill_gaps(pdf: pd.DataFrame) -> pd.DataFrame:
    pdf = pdf.sort_values("day")
    pdf["amt"] = pdf["amt"].interpolate().ffill()
    return pdf

(sales.groupBy("store")
      .applyInPandas(fill_gaps, schema=sales.schema)

9.4.2 mapInPandas: 파티션별 pandas 처리

def only_big(it):
    for pdf in it:
        yield pdf[pdf["amt"] > 6]

10.3 AQE: 실행 중 재최적화

Adaptive Query Execution(3.2+ 기본 활성)은 셔플이 끝날 때마다 실제 통계를 보고 남은 계획을 다시 짭니다. 정적인 추정치의 한계를 보완하는 장치로, 세 가지 일을 합니다.

  1. 셔플 파티션 병합. spark.sql.shuffle.partitions=200이어도 실제 데이터가 작으면 작은 파티션들을 합쳐 Task 수를 줄입니다. 목표 크기는 spark.sql.adaptive.advisoryPartitionSizeInBytes(기본 64MB).
  2. 조인 전략 전환. 셔플 후 한쪽이 작다고 밝혀지면 Sort Merge를 Broadcast로 바꿉니다(6장에서 확인).
  3. 스큐 조인 처리. 유난히 큰 파티션을 여러 조각으로 쪼개고 상대편을 복제해 조인합니다.

그래서 요즘은 shuffle.partitions를 넉넉히(데이터에 비해 크게) 잡고 AQE가 줄이게 두는 방식이 일반적입니다. explain()에서 AdaptiveSparkPlan, AQEShuffleRead가 보이면 AQE가 일하는 중입니다.

10.4 데이터 스큐

증상: Stage의 Task 199개는 몇 초 만에 끝났는데 1개가 수십 분째 돌고 있다. Spark UI의 Task 지표에서 Duration·Shuffle Read Size의 Max가 Median의 수십 배.

원인: 특정 키에 데이터가 몰림. null 키, "unknown", 기본값, 초대형 고객 등.

  1. 불필요한 키 걸러내기. null·더미 키가 원인이면 조인 전에 빼고 나중에 붙입니다. 가장 싸고 흔한 해결책입니다.
  2. 브로드캐스트. 상대편이 작으면 셔플 자체를 없앱니다.
  3. AQE 스큐 조인. spark.sql.adaptive.skewJoin.enabled(기본 true). 조인에서 자동 처리되지만 집계와 윈도에는 적용되지 않습니다.

    # 2단계: 키별 최종 집계
    .groupBy("k").agg(F.sum("c").alias("count")))
salted.orderBy(F.desc("count")).show(3)

10.5 셔플 줄이기 체크리스트

  • 필터와 컬럼 선택을 최대한 앞으로. 옵티마이저가 대부분 해 주지만, UDF나 캐시 경계를 넘지는 못합니다.
  • 조인 전에 집계. 1억 행을 조인하고 집계하기보다, 먼저 집계해 10만 행으로 줄인 뒤 조인합니다.
  • distinct·orderBy는 필요할 때만. 둘 다 전체 셔플입니다. 결과를 보기 좋게 하려는 정렬은 마지막 작은 결과에만.
  • 작은 쪽은 브로드캐스트.
  • 같은 키로 반복 조인한다면 버킷팅. bucketBy(n, "key").saveAsTable(...)로 저장한 테이블끼리는 같은 키 조인 시 셔플이 생략됩니다. 관리 비용이 있어 반복 조인이 확실할 때만 씁니다.

10.6 작은 파일 문제

파일 수만 개짜리 테이블은 읽을 때마다 파일 목록 조회와 열기 비용이 데이터 처리 시간을 압도합니다. 스트리밍·잦은 append·과도한 partitionBy가 주범입니다.

  • 쓰기 전에 repartition/coalesce로 파일 수를 조절합니다. 목표는 파일당 128MB–1GB.
  • 읽는 쪽에서는 spark.sql.files.maxPartitionBytes가 작은 파일들을 한 Task로 묶어 줍니다(파일 열기 비용은 남음).
  • Delta/Iceberg는 OPTIMIZE·rewrite_data_files로 주기적 컴팩션을 지원합니다.

10.7 메모리와 스필

Executor 메모리는 대략 이렇게 나뉩니다.

  • 실행(execution) 메모리: 셔플·조인·정렬·집계의 작업 공간.
  • 저장(storage) 메모리: 캐시, 브로드캐스트 변수. 실행 메모리와 경계가 유동적입니다(unified memory).
  • 오버헤드(overhead): JVM 힙 밖. Python 워커와 Arrow 버퍼가 여기를 씁니다. pandas UDF를 많이 쓰면 spark.executor.memoryOverhead(또는 spark.executor.pyspark.memory)를 늘려야 할 수 있습니다. 컨테이너가 이유 없이 죽는다면(YARN/K8s의 OOMKilled) 대개 이쪽입니다.

실행 메모리가 부족하면 Spark는 중간 데이터를 디스크에 스필(spill) 하고 계속 진행합니다. UI의 Spill (Memory/Disk)가 크면 파티션당 데이터가 너무 많다는 신호입니다. 파티션 수를 늘리십시오.

10.9 안티패턴 모음

  • 중간 확인용 count()/show()를 파이프라인 곳곳에 남겨 두기 → 매번 전체 재실행.
  • 큰 DataFrame에 collect(), toPandas() → Driver OOM.
  • for 루프로 withColumn 수십 번 → 계획 폭발. select/withColumns로.
  • for 루프로 필터 조건마다 따로 쿼리 → 한 번의 groupBy나 when으로.
  • 내장 함수로 되는 일을 UDF로.
  • 고카디널리티 컬럼으로 partitionBy → 작은 파일 수백만 개.
  • 스키마 추론(inferSchema)에 기대기 → 이중 스캔, 타입 불안정.

10.10 핵심 정리

  • 적게 읽고, 적게 옮기고, 고르게 나누기.
  • 캐시는 여러 번 쓰는 결과에만, 다 쓰면 unpersist.
  • repartition은 셔플, coalesce는 병합. 파일 수 조절에 씁니다.
  • AQE가 파티션 병합·조인 전환·스큐 조인을 자동 처리합니다.
  • 스큐는 진단(키 분포) → 걸러내기/브로드캐스트/솔팅.

11 RDD: 알아는 두어야 할 저수준 API

RDD(Resilient Distributed Dataset)는 Spark 초기의 핵심 추상화입니다. DataFrame은 RDD 위에 스키마와 옵티마이저를 얹은 것이고, 지금도 모든 DataFrame 연산은 결국 RDD 연산으로 실행됩니다.

새 코드에서 RDD를 쓸 이유는 거의 없습니다. RDD 연산은 옵티마이저의 도움을 받지 못하고, PySpark에서는 모든 연산이 Python 람다라 UDF처럼 직렬화 비용을 치릅니다. Spark Connect에서는 아예 쓸 수 없습니다. 그래도 옛 코드를 읽고, 가끔 필요한 저수준 조작을 하려면 개념은 알아야 합니다.

11.1 RDD라는 이름의 뜻

  • Resilient: 각 RDD는 자신이 어떤 부모에서 어떤 연산으로 만들어졌는지(계보, lineage)를 기억합니다. Executor가 죽어 파티션을 잃으면, 데이터를 복제해 두는 대신 계보를 따라 그 파티션만 다시 계산합니다. Spark 장애 복구의 기본 원리이고, DataFrame에도 그대로 적용됩니다.
  • Distributed: 파티션으로 나뉘어 클러스터에 흩어져 있습니다.
  • Dataset: 임의의 Python 객체의 모음입니다. 스키마가 없습니다.

11.2 맛보기

  • 큰 사전·모델을 UDF 안에서 쓸 때 클로저로 잡는 대신 sc.broadcast로 감싸면 Task마다가 아니라 Executor마다 한 번 전송됩니다.
  • 어큐뮬레이터는 액션 안에서만 정확합니다. 변환(map) 안에서 더한 값은 Task 재시도나 재계산 때 중복 집계될 수 있습니다. 비즈니스 수치가 아니라 대략적인 모니터링 용도로만 쓰십시오.

11.6 핵심 정리

  • RDD = 계보를 기억하는 분산 컬렉션. 장애 복구의 원리입니다.
  • 새 코드는 DataFrame. RDD는 읽을 줄만 알면 됩니다.
  • groupByKey 대신 reduceByKey. 브로드캐스트는 Executor당 1회 전송.

12 Structured Streaming

12.1 핵심 아이디어: 끝없이 늘어나는 테이블

Structured Streaming은 스트림을 계속 행이 추가되는 무한한 테이블로 봅니다. 여러분은 이 테이블에 대해 평소처럼 DataFrame 쿼리를 쓰고, Spark는 새 데이터가 들어올 때마다 그 쿼리를 증분으로 실행해 결과를 갱신합니다.

그래서 배치 코드와 스트리밍 코드가 거의 같습니다. spark.read → spark.readStream, df.write → df.writeStream으로 바뀌는 정도입니다.

기본 실행 방식은 마이크로 배치입니다. 트리거 간격마다 새로 도착한 데이터를 작은 배치로 처리합니다. 지연 시간은 보통 수백 ms ~ 수 초입니다.

12.4 이벤트 시간과 워터마크

스트림 데이터는 늦게 도착합니다. 10:00의 이벤트가 네트워크 문제로 10:05에 들어올 수 있지요. Spark는 이벤트 시간(ts) 기준으로 윈도를 계산하고, 늦게 온 데이터도 해당 윈도에 반영합니다.

문제는 “언제까지 기다리느냐”입니다. 무한히 기다리면 모든 윈도의 상태를 영원히 들고 있어야 합니다. 워터마크가 그 한도입니다.

.withWatermark("ts", "2 minutes")

“지금까지 본 가장 늦은 이벤트 시각 − 2분”보다 오래된 윈도는 닫힌 것으로 간주합니다. 닫힌 윈도의 상태는 메모리에서 지우고, 그보다 늦게 온 데이터는 버립니다. append 모드에서는 윈도가 닫혀야 결과가 한 번 출력됩니다.

워터마크 없이 스트리밍 집계를 돌리면 상태가 끝없이 커져 결국 메모리가 터집니다. 스트리밍 집계·조인·중복 제거에는 워터마크를 거십시오. 중복 제거는 dropDuplicatesWithinWatermark(3.5+)가 편합니다.

12.6 체크포인트와 정확히 한 번

checkpointLocation에는 처리한 소스 오프셋, 집계 상태, 커밋 로그가 저장됩니다. 쿼리가 죽었다가 재시작되면 여기서 이어 갑니다. 재생 가능한 소스(Kafka, 파일)와 멱등 싱크(파일, Delta)를 조합하면 exactly-once가 보장됩니다.

체크포인트는 쿼리의 정체성입니다. 쿼리 로직(특히 집계 키나 상태 구조)을 크게 바꾸면 기존 체크포인트와 호환되지 않을 수 있습니다. 운영 중인 스트림을 바꿀 때는 새 체크포인트 경로로 시작하는 계획을 세우십시오. 체크포인트는 반드시 영속 저장소(S3, HDFS)에 두십시오.

def upsert(batch_df, batch_id):
    batch_df.createOrReplaceTempView("updates")
    batch_df.sparkSession.sql("""
        MERGE INTO target t USING updates u
        ON t.id = u.id
        WHEN MATCHED THEN UPDATE SET *
        WHEN NOT MATCHED THEN INSERT *
    """)

orders.writeStream.foreachBatch(upsert) \
      .option("checkpointLocation", ckpt).start()

13 배포, 테스트, 디버깅

13.1 애플리케이션 구조

노트북에서 짠 코드를 운영에 올릴 때는 다음 모양을 권합니다.

# jobs/daily_sales.py
import argparse
from pyspark.sql import SparkSession, DataFrame
from pyspark.sql import functions as F

def transform(orders: DataFrame, users: DataFrame
              ) -> DataFrame:
    """순수 변환: I/O 없음 → 단위 테스트 가능"""
    return (orders.join(F.broadcast(users), "user")
                  .groupBy("dt", "tier")
                  .agg(F.sum("amount").alias("amt")))

def main():
    p = argparse.ArgumentParser()
    p.add_argument("--dt", required=True)
    args = p.parse_args()

    spark = (SparkSession.builder
             .appName(f"daily_sales:{args.dt}")
             .getOrCreate())
    orders = spark.read.table("raw.orders") \
                  .where(F.col("dt") == args.dt)
    users = spark.read.table("dim.users")
    (transform(orders, users)
        .write.mode("overwrite")
        .option("partitionOverwriteMode", "dynamic")
        .insertInto("mart.daily_sales"))
    spark.stop()

if __name__ == "__main__":
    main()

핵심은 I/O와 변환의 분리입니다. transform은 DataFrame을 받아 DataFrame을 돌려주는 순수 함수이므로 작은 입력으로 테스트할 수 있습니다. 여러 변환을 이어 붙일 때는 df.transform(f) 체이닝이 깔끔합니다.

result = (raw.transform(clean)
             .transform(enrich, users)   # 3.3+ 인자 전달
             .transform(aggregate))

  • deploy-mode: client는 Driver가 submit한 머신에서, cluster는 클러스터 안에서 돕니다. 운영 배치는 cluster가 일반적입니다.

  • 동적 할당(dynamicAllocation): 작업량에 따라 Executor 수를 늘리고 줄입니다. 공유 클러스터에서 권장됩니다.
  • Python 의존성: 순수 Python 모듈은 --py-files(zip), 네이티브 확장이 있는 패키지(pandas, numpy 등)는 venv-pack/conda-pack으로 환경 전체를 압축해 --archives로 배포하고 PYSPARK_PYTHON=./environment/bin/python을 지정합니다. Kubernetes라면 의존성을 담은 컨테이너 이미지가 가장 깔끔합니다.
  • JVM 패키지(Kafka 커넥터, Delta 등): --packages groupId:artifactId:version.

Databricks, EMR, Dataproc 같은 관리형 플랫폼은 이 설정의 상당 부분을 대신 해 주지만, 개념은 같습니다.

13.3 테스트

pytest 픽스처로 로컬 세션 하나를 테스트 세션 전체에서 공유합니다. 세션 생성은 수 초가 걸리므로 테스트마다 만들지 마십시오.

# conftest.py
import pytest
from pyspark.sql import SparkSession

@pytest.fixture(scope="session")
def spark():
    s = (SparkSession.builder.master("local[2]")
         .config("spark.sql.shuffle.partitions", "2")
         .config("spark.ui.enabled", "false")
         .getOrCreate())
    yield s
    s.stop()

shuffle.partitions를 작게 잡는 것만으로 테스트 속도가 크게 달라집니다. 비교에는 pyspark.testing의 도우미(3.5+)를 씁니다.

from pyspark.testing import (assertDataFrameEqual,
                             assertSchemaEqual)
from pyspark.sql import functions as F

def transform(orders, users):
    return (orders.join(users, "user")
                  .groupBy("tier")
                  .agg(F.sum("amount").alias("amt")))

orders = spark.createDataFrame(
    [("kim", 10), ("lee", 5), ("kim", 7)],
    "user STRING, amount INT")
users = spark.createDataFrame(
    [("kim", "gold"), ("lee", "basic")],
    "user STRING, tier STRING")
expected = spark.createDataFrame(
    [("gold", 17), ("basic", 5)],
    "tier STRING, amt BIGINT")

actual = transform(orders, users)
assertDataFrameEqual(actual, expected)   # 행 순서 무시
assertSchemaEqual(actual.schema, expected.schema)
print("ok")
ok

assertDataFrameEqual은 기본적으로 행 순서를 무시하고, 실패하면 어떤 행이 다른지 diff를 보여 줍니다. sum(INT)의 결과가 BIGINT라는 것처럼, 스키마 테스트가 예상치 못한 타입 변화를 잡아 주는 경우가 많습니다.

13.4 Spark UI 읽는 법

느린 작업을 조사하는 순서입니다(로컬은 localhost:4040, 끝난 작업은 History Server).

  1. SQL / DataFrame 탭: 쿼리별 실행 계획이 그래프로 나오고, 각 노드에 실제 행 수·시간·셔플 크기가 찍힙니다. explain()의 실측 버전입니다. 어디서 행 수가 폭발했는지(조인 키 중복), 어떤 조인 전략이 쓰였는지 여기서 확인합니다.
  2. Stages 탭: 가장 오래 걸린 Stage를 엽니다. Summary Metrics 표에서 Duration·Shuffle Read의 Min/Median/Max를 봅니다. Max가 Median의 몇 배 이상이면 스큐입니다.
  3. 같은 표에서 Spill이 크면 파티션당 데이터가 너무 많습니다 → 파티션 수 늘리기.
  4. GC Time이 Duration의 10%를 넘으면 메모리 압박입니다.
  5. Executors 탭: 실패한 Task, 죽은 Executor, 캐시 사용량.
  6. Storage 탭: 캐시된 데이터의 크기와 메모리/디스크 비율.

13.7 핵심 정리

  • 변환은 순수 함수로 분리하고 df.transform으로 잇기 → 테스트 가능.

  • 에러는 대괄호 속 에러 클래스부터 읽습니다.
